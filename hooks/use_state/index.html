    use_state

    use_state gives a component a value that persists across renders, and a setter that changes it. Setting a different value re-renders the component.

    @component
def counter() -> Div:
    count, set_count = use_state(0)

    def on_input(event: InputEvent, _: Receiver) -> InputResponse:
        match event:
            case KeyPressed(key="+"):
                set_count(lambda count: count + 1)
                return ()
            case KeyPressed(key="-"):
                set_count(lambda count: count - 1)
                return ()
            case KeyPressed(key="0"):
                set_count(0)
                return ()
            case _:
                return None

    return Div(
        style=col | border | border_lightrounded | pad_x(1),
        on_input=on_input,
        children=(
            Text(content=f"Count: {count}", style=text_color("amber", 400)),
            Text(content="+ and - count, 0 resets", style=text_color("slate", 400)),
        ),
    )


    ╭────────────────────────────╮
│ Count: 3                   │
│ + and - count, 0 resets    │
╰────────────────────────────╯

    Each key press sets the count, which renders counter again with the new value:

    + and - pass the setter a function, since the new count depends on the old one (see below), and 0 passes it a value, since the reset doesn't.

    Updating state from its previous value

    When the new state depends on the old, pass the setter a function

    count is the value as of the render that built the handler, and nothing updates it until the next render. A setter given a value replaces the state with it, so every update computed from count before the next render starts from the same stale count, and only the last one survives. No error is raised: the other updates just vanish.

    Given a function, the setter calls it right away with the latest state, updates included, and stores what it returns:

    set_count(count + 1)            # wrong: loses updates made since this render
set_count(lambda c: c + 1)      # right: builds on the latest state

    Several updates can land before the next render in ways that are easy to miss, because each looks like one update when you read the code.

    Two updates in one handler. Each by_value + 1 is computed from the same by_value, while each function builds on what the one before it returned:

    @component
def plus_two() -> Div:
    by_value, set_by_value = use_state(0)
    by_function, set_by_function = use_state(0)

    def on_input(event: InputEvent, _: Receiver) -> InputResponse:
        match event:
            case KeyPressed(key="+"):
                set_by_value(by_value + 1)
                set_by_value(by_value + 1)
                set_by_function(lambda n: n + 1)
                set_by_function(lambda n: n + 1)
                return ()
            case _:
                return None

    return Div(
        style=col | border | border_lightrounded | pad_x(1),
        on_input=on_input,
        children=(
            Text(content=f"By value:    {by_value}", style=text_color("red", 400)),
            Text(content=f"By function: {by_function}", style=text_color("emerald", 400)),
        ),
    )


    ╭────────────────────────────╮
│ By value:    3             │
│ By function: 6             │
╰────────────────────────────╯

    After three presses of +, by_value has gone up by one a press, and by_function by two.

    Key presses that arrive together. Counterweight routes every event it has read before rendering again, and a terminal delivers keys together whenever they come faster than one per frame: fast typing, a held key repeating, or text pasted into a terminal without bracketed paste. Each key press's handler sees the same text:

    text, set_text = use_state("")


def on_input(event: InputEvent, _: Receiver) -> InputResponse:
    match event:
        case KeyPressed(key=key) if len(key) == 1:
            set_text(text + key)  # "abc" typed in one burst leaves text as "c"
            return ()
        case _:
            return None

    This one hides from tests: an autopilot renders after each event it sends, so every key press there sees the latest text, and so does slow typing by hand. Write set_text(lambda t: t + key). For a text field, use_text_input does this for you, along with the cursor, the editing keys and pastes.

    An effect that outlives its render. An effect closes over the values from the render that started it, and one with deps=() keeps them for as long as the component is mounted:

    count, set_count = use_state(0)


async def tick() -> None:
    while True:
        await asyncio.sleep(1)
        set_count(count + 1)  # count stays at 1, since this count is always 0


use_effect(tick, deps=())

    Pass a value only when the new state doesn't depend on the old, as in set_query("") to clear a field or set_selected(item.id) to select an item. Toggling a flag depends on it, so it takes a function too: toggle, as in set_open(toggle).

    The setter is the same object on every render, so a handler that updates state only through functions captures nothing that goes stale, and can be built once with use_memo or passed to a memo component.

    API

    counterweight.hooks.use_state 

    use_state(
    initial_value: Getter[T],
) -> tuple[T, Setter[T]]

    use_state(initial_value: T) -> tuple[T, Setter[T]]

    use_state(
    initial_value: Getter[T] | T,
) -> tuple[T, Setter[T]]
    PARAMETER DESCRIPTION
    initial_value

    The initial value of the state. It can either be the initial value itself, or a zero-argument function that returns the initial value.

    TYPE: Getter[T] | T

    RETURNS DESCRIPTION
    T

    The current value of the state (i.e., for the current render cycle).
    Setter[T]

    A function that can be called to update the value of the state (e.g., in an event handler). It can either be called with the new value of the state, or a function that takes the current value of the state and returns the new value of the state. When the new value depends on the current one, pass a function: a value computed from the state a render saw loses every update made since, such as from other key presses read before the next render (see Updating state from its previous value). If the value is not equal to the current of the state, Counterweight will trigger a render cycle. It is the same object on every render, so it can be left out of an effect's deps, and including it never reruns the effect. Once the component unmounts, calling it does nothing.

    counterweight.hooks.toggle 

    toggle(value: bool) -> bool

    Flips a flag: pass it to a use_state setter, as set_open(toggle), so each toggle flips the latest value, even when several land before the next render. It takes only a bool, so a type checker rejects it for state of any other type, where operator.not_ would quietly turn the state into one.

    counterweight.hooks.Getter 

    Getter = Callable[[], T]

    A function that computes a value, such as the initial state use_state computes only on the first render.

    counterweight.hooks.Setter 

    Setter = Callable[[Callable[[T], T] | T], None]

    What use_state returns to set its state: given a value, the next state, or given a function, the next state computed from the latest one.
