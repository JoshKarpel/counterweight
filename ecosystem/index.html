    Ecosystem

    This page places Counterweight next to the three terminal UI frameworks closest to it: Textual, Ink and Ratatui. It covers how each one is programmed, what each one has that Counterweight doesn't, and when you'd pick each. It doesn't benchmark them.

    Where Counterweight fits

    Counterweight is a Python framework with React's programming model. Each of the others shares one of those with it:

    • Textual is also Python, but you build its UIs from widget objects that you query and update.
    • Ink is also React (it's a renderer for React itself), but you write it in JavaScript or TypeScript.
    • Ratatui shares neither, but Counterweight draws to the terminal the way Ratatui does, by painting every frame into a buffer and writing only the cells that changed.

    So the short version is: choose Counterweight over Textual for the programming model, over Ink to write Python, and over Ratatui to have the framework own the state, the event loop and the layout.

    Textual

    Textual is the closest alternative in the same language, and the most complete: it has a large widget library with data tables, trees, tabs, select menus, checkboxes and progress bars, text selection, visible scrollbars, an inline mode, Windows support, and a way to serve apps in a browser.

    The difference is how you describe a UI. In Textual, a UI is a tree of widget objects that live across renders. You change it by setting reactive attributes, by querying for widgets and calling methods on them, and by handling messages that bubble up the tree. What the screen shows at any moment depends on the history of those changes.

    In Counterweight, a UI is a function of state. Components are functions that return elements, and every change to state renders the tree again from those functions, so what the screen shows depends only on the current state. A component's props are its function arguments, so a type checker checks every place a component is used.

    Styling differs in the same direction. Textual's TCSS stylesheets match widgets by type, ID and class from a separate file or class variable, with a cascade deciding which rule wins. Counterweight's styles are values written on the element they style, so you can see what an element looks like without looking anywhere else.

    Layout differs too. Textual's grid has its own rules, and it has no flexbox. Counterweight's layout is the web's flexbox and grid, so what you know from CSS carries over (see Layout).

    Choose Textual when you need its widgets, Windows, inline mode or the browser, or a framework that many apps already depend on.

    Ink

    Ink is React itself, rendering to the terminal. Its README lists Claude Code, Gemini CLI and GitHub Copilot CLI among the tools built with it. If you know Ink, you know most of Counterweight: components, use_state, use_effect, use_ref, use_memo, keys and memo all follow React's rules (see Components). Both render only the components whose state changed and the components they return, skipping memo components whose arguments are unchanged.

    The main reason to choose Counterweight over Ink is Python. A Counterweight app runs in the same process as the Python libraries it presents, such as a model client, a data pipeline or a test runner, with no separate service between them.

    Beyond the language:

    • Effects are async functions. Where a React effect returns a cleanup function, a Counterweight effect is cancelled when its dependencies change or its component unmounts, so cleanup goes in a try/finally block (see use_effect).
    • Counterweight lays out with grid as well as flexbox.
    • Counterweight has mouse input, through on_input handlers and the use_mouse and use_hovered hooks. Ink has none.

    Ink renders inline by default, below the shell prompt, and its <Static> component writes output that stays in the terminal's scrollback. Counterweight always takes over the whole screen. Choose Ink for a command-line tool whose output should stay in the scrollback, or when your code is already in JavaScript.

    Ratatui

    Ratatui is an immediate-mode library: it keeps no tree of your UI between frames. Each frame, your code draws widgets into a screen-sized buffer, and Ratatui writes the cells that differ from the previous frame's buffer. Your code owns the event loop, the input handling and all of the state.

    Counterweight owns all three. It keeps the component tree and its state between renders, reads input, calls your handlers, and renders again when state changes. Its output stage works like Ratatui's: every render paints a full buffer, diffs it against the last one, and writes only the changes.

    Their layout models differ. Ratatui splits an area by constraints on the parent, while Counterweight uses flexbox and grid, where content can size its container. Coming from Ratatui? shows the equivalents of Ratatui's constraints, and where they behave differently.

    Choose Ratatui for a single compiled binary, for full control over when and what you draw, or when frame time is the constraint: Counterweight renders in Python, and Ratatui in Rust.

    What Counterweight doesn't do

    These are the gaps you're most likely to hit, with what to do instead:

    • Text selection, and scrolling a long line. use_text_input and use_text_area have no selection, and a single-line value wider than its box doesn't scroll to keep the cursor in view. Tracked in #420 (scrolling a long line).
    • Inline rendering. Counterweight always uses the terminal's alternate screen, so nothing it draws remains in the scrollback when the app exits. Tracked in #393.
    • Windows. Counterweight reads input through POSIX terminal APIs, and is tested on Linux and macOS.
    • A widget library. Counterweight's widgets are a text input and a text area, and its rich text renders Markdown and highlighted code. Tables, trees, menus, tabs and the rest you build from elements, layout, styles and hooks.
